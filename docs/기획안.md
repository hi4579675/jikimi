# 계약지킴이 - 소상공인 임대차 계약 AI 분석 서비스

📅 작성일: 2026년 4월 1일  
👥 팀 구성: 미정  

---

## 1. 프로젝트 개요

계약지킴이는 소상공인이 임대차 계약서(PDF/이미지)를 업로드하면,  
**OCR → 구조화 → RAG 기반 법령 대조 → 독소 조항 리포트**를 자동 생성하는 AI 서비스입니다.

### 개발 배경

어머니가 식당을 4년째 운영 중이며, 건물주와의 임대차 계약 만료를 앞두고  
계약서 검토를 변호사에게 맡기기 부담스러워 그냥 서명하려 하셨습니다.  
이 경험을 출발점으로 실제 수요가 있는 서비스를 직접 만들고자 합니다.

### 기술 목표

- FastAPI 기반 AI 파이프라인 (OCR → RAG → LLM) 설계 및 구현
- Spring Boot와 FastAPI의 역할 분리 아키텍처 실증
- 실제 배포 경험 (AWS + CI/CD + Docker)
- 실사용자(어머니) 테스트를 통한 UX 개선 과정 기록

## 2. 시장 분석

### TAM (전체 시장)
- 국내 임대차 계약 체결 건수: 연간 약 200만 건 (상가 + 주거)
- 상가 임차인: 약 100만 건/년

### SAM (유효 시장)
- 계약 갱신 시점의 소상공인 중 디지털 서비스 사용 가능자
- 약 30만 명/년 (스마트폰 보유 + 앱 사용 가능)

### SOM (실제 목표 시장, 1~2년)
- 초기 타겟: 서울/수도권 자영업자 중 SNS·카카오 채널 유입
- 목표 MAU: 3,000명 (1년차)
- 목표 유료 전환: 500명 (월 9,900원 플랜)

### 경쟁 분석

| 서비스 | 특징 | 한계 |
|---|---|---|
| 로톡 | 변호사 매칭 | 비용 높음, 즉각 분석 없음 |
| 네이버 지식iN | 무료 답변 | 개인화 없음, 신뢰도 불균일 |
| 일반 법률 챗봇 | 일반 질의응답 | 계약서 직접 분석 불가 |
| **계약지킴이** | **계약서 업로드 → 즉시 분석** | 개발 중 |

## 3. 전체 시스템 아키텍처

### 3-1. 역할 분담 설계

| | Spring Boot | FastAPI |
|---|---|---|
| **주요 역할** | 사용자 인증/인가, 계약 이력 CRUD, 알림 스케줄링, 결제 | OCR 파이프라인, 벡터 검색, LLM 호출, 문서 전처리 |
| **선택 이유** | 엄격한 트랜잭션 정합성, 스케줄링 안정성 (Spring Batch) | 비동기 AI 추론, Python ML 생태계 활용 |
| **DB 접근** | PostgreSQL (JPA) | pgvector (벡터 통합), Redis (캐시) |
| **통신** | REST API (외부 클라이언트) | 내부 REST API (Spring Boot → FastAPI 라우팅) |

### 3-2. 요청 흐름

```
① 사용자가 계약서 이미지/PDF 업로드
② Spring Boot: 인증 확인 → S3 저장 → FastAPI로 분석 요청 라우팅
③ FastAPI: OCR 전처리 → 텍스트 구조화(AST) → Hybrid RAG 검색 → LLM 분석
④ 분석 결과 JSON 반환 → Spring Boot DB 저장 → 사용자에게 리포트 응답
```

## 4. 핵심 기술 상세

### 4-1. OCR 전처리 파이프라인

| 단계 | 기술 | 처리 내용 |
|---|---|---|
| 1단계 (MVP) | pdfplumber | 텍스트 레이어 있는 PDF 직접 파싱 (OCR 불필요) |
| 2단계 | Clova OCR | 기울기/밝기 이슈 없는 환경에서 정확도 검증 |
| 3단계 | Clova OCR + OpenCV | 핸드폰 촬영 이미지 대응 (기울기 보정, 밝기 정규화 전처리 추가) |

### 4-2. AST 기반 계약서 구조화

단순 텍스트 매칭이 아닌, 계약서의 각 조(Article)를 객체로 파싱하여 구조적으로 법령과 대조합니다.

```json
{
  "article_id": "제3조",
  "title": "임대료",
  "content": "임대료는 월 300만 원으로 하며...",
  "risk_flag": null,
  "legal_ref": "상가건물 임대차보호법 제11조"
}
```

### 4-3. Hybrid RAG 파이프라인

키워드 검색과 의미 검색을 결합하여 법령 조항 번호(예: 제11조)와 판례 의미 모두를 커버합니다.

| 검색 방식 | 용도 | 도구 |
|---|---|---|
| BM25 (Sparse) | 법령 조항 번호, 조문 키워드 매칭 | LangChain BM25Retriever |
| Vector Search (Dense) | 판례·사례의 의미 기반 검색 | pgvector + text-embedding-3-small |
| 결과 통합 | 두 검색 결과 RRF로 병합 후 LLM 컨텍스트 전달 | LangChain EnsembleRetriever |

### 4-4. 지식베이스 구성

- 상가건물 임대차보호법 전문 (국가법령정보센터 API — 공공데이터)
- 민법 임대차 관련 조항
- 대법원 공개 판례 데이터
- 어머니 실제 계약서 (비식별화 처리 후 테스트셋으로 활용)

## 5. 기술 스택

| 영역 | 선택 기술 | 선택 이유 |
|---|---|---|
| AI 서버 | FastAPI + Python | LangChain, pgvector 등 AI 라이브러리 연동 자연스럽고, 비동기 처리로 AI 추론 속도에 유리 |
| 백엔드 | Spring Boot | 로그인·계약 이력 저장·만료일 알림 등 트랜잭션 처리에 적합 |
| LLM | GPT-4o API | 한국어 법률 문서 이해도 높음. 추후 오픈소스 모델 교체 가능성 열어둠 |
| RAG 프레임워크 | LangChain | 청킹·리트리버·체인 구성 등 RAG 컴포넌트가 잘 구현되어 있어 개발 속도에 유리 |
| 벡터 DB | PostgreSQL + pgvector | 별도 벡터 DB 없이 PostgreSQL 익스텐션으로 통합, 운영 복잡도 최소화 |
| OCR | Naver Clova OCR | 한국어 인식률이 핵심. EasyOCR 대비 정확도 높고 Free 플랜으로 초기 비용 없이 시작 가능 |
| RDB | PostgreSQL | pgvector 지원으로 관계형 데이터와 벡터 데이터를 하나의 DB로 통합 관리 |
| 캐시 | Redis | 동일 계약서 반복 분석 시 LLM API 비용 절감 및 응답속도 개선 |
| 파일 저장 | AWS S3 | 높은 내구성과 확장성, IAM으로 계약서 같은 민감 문서 안전하게 관리 |
| 알림 | Spring Batch + FCM | 미정 |
| 프론트 | 미정 | MVP 우선 |
| 인프라 | 미정 | 미정 |
| CI/CD | 미정 | 미정 |
