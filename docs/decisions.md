## [2026-04-01] FastAPI + Spring Boot 이중 서버 분리

**결정**: AI 파이프라인은 FastAPI, 비즈니스 로직은 Spring Boot로 분리한다.

**이유**
- FastAPI는 Python 기반으로 LangChain, pgvector 등 AI 라이브러리와 자연스럽게 연동된다
- Spring Boot는 JPA 트랜잭션, 스케줄링(만료일 알림) 등 비즈니스 로직에 적합하다
- 두 기술을 함께 보여줄 수 있어 포트폴리오 관점에서도 유리하다

**트레이드오프**
- 이 프로젝트 규모에서는 단일 서버 대비 운영 복잡도가 올라간다
- JWT secret key 공유, 에러 응답 형식 통일 등 서버 간 계약을 별도로 관리해야 한다
- WebClient timeout을 반드시 명시해야 한다 (OCR/LLM 지연 시 Spring Boot 스레드 블락 방지)

## [2026-04-01] pgvector 선택 (ChromaDB 대신)

**결정**: 벡터 스토어로 ChromaDB 대신 PostgreSQL + pgvector를 사용한다.

**이유**
- 관계형 데이터(계약 이력, 사용자)와 벡터 데이터(법령 임베딩)를 단일 DB로 관리할 수 있다
- 별도 벡터 DB 프로세스를 운영하지 않아 운영 포인트가 줄어든다
- 이 프로젝트 지식베이스 규모(상가임대차보호법 + 민법 + 판례 수천 건)는 pgvector로 충분하다

**트레이드오프**
- ChromaDB 대비 초기 세팅이 다소 복잡하다 (익스텐션 설치, HNSW 인덱스 설정 필요)
- 수십만 벡터 이상으로 지식베이스가 커지면 전용 벡터 DB 마이그레이션을 검토한다

**주의**: HNSW 인덱스 필수
```sql
CREATE INDEX ON law_chunks USING hnsw (embedding vector_cosine_ops);
```

## [2026-04-01] OCR 단계적 도입 (pdfplumber → Clova OCR)

**결정**: MVP에서는 pdfplumber만 사용하고, Clova OCR은 Phase 2에서 도입한다.

**이유**
- MVP 범위를 "텍스트 레이어 있는 PDF"로 좁히면 OCR 복잡도 없이 빠르게 PoC 검증이 가능하다
- Clova OCR Free 플랜은 한국어 인식률이 높고 초기 비용이 없어 Phase 2 도입에 적합하다
- 핸드폰 촬영 이미지 대응(기울기 보정, 밝기 정규화)은 OpenCV 전처리가 필요하므로 별도 단계로 분리한다

**트레이드오프**
- MVP에서 스캔본·촬영 이미지 지원 불가 → 사용자에게 명확히 안내 필요

## [2026-04-01] 조항 단위 청킹 전략

**결정**: 일반 fixed-size 청킹 대신 계약서 조(Article) 단위로 파싱한다.

**이유**
- fixed-size 청킹은 "제11조 (임대료) 월 300만 원..." 같은 문장을 조항 경계와 무관하게 자를 수 있어 법령 대조 품질이 떨어진다
- 조항 단위로 파싱하면 각 조항을 하나의 의미 단위로 법령과 1:1 대조할 수 있다

**트레이드오프**
- 조항이 너무 길면(3~4개 항이 합쳐진 경우) 토큰 초과 가능성이 있다
- 조항 내 "항" 단위로 서브청킹하는 fallback 로직이 필요하다

## [2026-04-01] Hybrid RAG (BM25 + Vector Search)

**결정**: BM25(Sparse)와 pgvector(Dense)를 RRF로 병합하는 Hybrid RAG를 사용한다.

**이유**
- BM25만 쓰면 법령 조항 번호(제11조 등) 키워드는 잘 잡히지만 판례·사례의 의미 검색이 약하다
- Vector Search만 쓰면 정확한 조문 번호 매칭이 불안정하다
- 두 방식을 RRF로 병합하면 조문 번호 패턴과 의미 기반 검색을 모두 커버할 수 있다

**트레이드오프**
- 법률 고유어(차임, 보증금, 묵시적 갱신 등)는 형태소 분석기(Kiwi) 또는 도메인 사전 등록이 필요할 수 있다 → PoC 결과 보고 판단

## [2026-04-01] LLM GPT-4o 선택

**결정**: 현재 공개 모델 중 GPT-4o를 사용한다.

**이유**
- 한국어 법률 문서 이해도가 현재 공개 모델 중 가장 높다고 판단
- 비용 부담이 있어 추후 오픈소스 모델(예: HyperCLOVA X) 교체 가능성을 열어둔다

**트레이드오프**
- API 비용 발생 → Redis 캐싱으로 동일 계약서 반복 분석 시 LLM 호출 생략
- 외부 API 의존성 → OpenAI 장애 시 서비스 전체 영향
