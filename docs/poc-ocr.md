# PoC (Proof of Concept) 검증 기록

작성일: 2026-04-01  
단계: Phase 0 — 기술 검증

---

## PoC란 무엇인가

PoC는 "이게 실제로 되는지 확인하는 단계"다.  
전체 시스템을 만들기 전에 핵심 기능이 동작하는지 먼저 검증한다.

Spring으로 치면 전체 서비스 붙이기 전에 핵심 로직만 JUnit으로 먼저 테스트해보는 것과 비슷한 개념이다.

---

## 왜 PoC가 필요했나

이 프로젝트의 핵심 리스크는 두 가지였다.

**OCR 정확도** — pdfplumber가 계약서를 제대로 읽을 수 있는가?  
**RAG 품질** — 관련 법령 검색 결과가 실제로 쓸만한가?

만약 Spring Boot + FastAPI 전체 구조를 다 만든 뒤에 OCR이 계약서를 못 읽거나,  
RAG 검색 결과가 엉망이면 구조째 갈아엎어야 한다.  
그래서 핵심 리스크를 먼저 검증하고 뼈대를 잡는 순서를 택했다.

## OCR PoC 과정에서 부딪힌 문제들

### 문제 1. 법령 참조문이 조항으로 오탐
본문 중간의 `제10조의4제1항`, `제49조` 같은 법령 참조문이  
조항 번호로 잘못 인식되어 21개가 파싱됨 (실제 조항은 12개)

**해결:** 줄 시작(`^`) + 괄호 제목 패턴만 실제 조항으로 인식
```python
# 전: 본문 어디서나 제N조 잡힘
pattern = r'(제\d+조(?:의\d+)?)'

# 후: 줄 시작 + 괄호 제목이 바로 오는 경우만
pattern = r'(?m)^[ \t]*(제\d+조(?:의\d+)?)\s*[（(]'
```

### 문제 2. 페이지 번호가 조항 내용 중간에 끼어듦
`- 1 / 3 -` 가 제8조 본문 중간에 삽입되어 내용이 잘림

**해결:** 페이지 번호 앞뒤 줄바꿈까지 함께 제거
```python
cleaned = re.sub(r'\n*-\s*\d+\s*/\s*\d+\s*-\n*', '\n', raw)
```

### 문제 3. 서명란이 마지막 조항에 붙어버림
제12조 내용 뒤에 임대인/임차인 서명란 텍스트가 통째로 붙음

**해결:** `본 계약을 증명하기 위하여` 패턴 이후를 서명란으로 인식하고 잘라냄

### 문제 4. 별지 분리 실패
`별지)`가 본문 참조(`(별지)을`)와 실제 별지 시작(`\n별지)`) 두 곳에 존재해서  
첫 번째에서 잘려 별지 내용이 사라짐

**해결:** 줄 시작의 `\n별지)` 만 실제 별지로 인식
```python
annex_match = re.search(r'\n별지\)', cleaned)
```

### 문제 5. pdfplumber 줄 앞 공백 삽입
v2 계약서에서 `" 제2조(임대차기간)"` 처럼 조항 앞에 공백이 붙어있어서  
`^제` 패턴으로 매칭 실패할 수 있음

**해결:** `[ \t]*` 추가로 줄 앞 공백/탭 허용
```python
pattern = r'(?m)^[ \t]*(제\d+조(?:의\d+)?)\s*[（(]'
```

## 최종 파싱 파이프라인

```
PDF 업로드
    ↓
extract_text()   — pdfplumber로 텍스트 레이어 추출
    ↓
clean_text()     — 노이즈 제거 + 별지 분리 + 서명란 제거
    ↓
parse_articles() — 줄 시작 제N조(제목) 패턴으로 조항 파싱
    ↓
[조항 리스트]    — RAG, LLM 단계로 전달
[별지 텍스트]    — RAG 지식베이스에 추가 예정
```

## 설계 결정 기록

**Clova OCR 바로 붙이지 않은 이유**  
PoC 단계 목적은 파이프라인 연결 확인이지 OCR 정확도 측정이 아님.  
텍스트 레이어 있는 PDF는 pdfplumber로 충분하고, 외부 API 없이 빠르게 검증 가능.  
스캔 PDF, 핸드폰 촬영 이미지 대응은 MVP 단계에서 Clova OCR로 추가 예정.

**특약사항을 제거하지 않은 이유**  
특약사항은 임대인이 불리한 조건을 넣는 영역으로 독소 조항이 가장 많이 숨어있음.  
제거 대상이 아니라 LLM 분석 대상. RAG/LLM 단계 구현 시 별도 파싱 로직 추가 예정.

**어머니 계약서 테스트를 나중으로 미룬 이유**  
실제 사용자 계약서는 형식이 제각각이라 어떤 문제가 생길지 미리 알 수 없음.  
표준계약서 2종에서 동작 확인 후, 실제 계약서 테스트할 때 문제 보고 그때 대응하는 게  
오버엔지니어링 없이 리스크를 최소화하는 방법.
